# Version 0.2 implementation plan

Draft, 2026-11-21, for [v0.2-design.md](v0.2-design.md).

**How to read it:**

- Steps in order; each ends usable, tested and pushed, and the owner tries it on the VM where marked **(VM)**.
- Sizes are relative (S, M, L) as in the roadmap.
- Each step lists the files it touches and its checks.

## Step 1. Groundwork: paths, version, install (M)

**Why first:** every later step is then installable, and the RPM (step 9) is only packaging.

1. **`VERSION`** (0.2.0-dev): compiled in (`-DWPS_VERSION`).
   - `--version` for `wpsd`, `wpsctl`, `wps-shell`, `wps-compositor`.
   - `ping` answers with the version and the protocol number.
2. **Paths:** `WPS_LIBEXECDIR`, `WPS_DATADIR`, `WPS_PLUGINDIR` from `make PREFIX=` (default: the tree, as now), with environment overrides.
   - Places that find each other today: `tools/wps-session` (REPO), `tools/install-extension.sh` (unit's ExecStart), `tools/install-session.sh`, the GNOME extension (where it starts `wps-shell`), `service/plugins.c` (`/proc/self/exe` sibling: keep, as `/usr/libexec/wps` holds both), data the desktop reads (sounds, wallpaper, icons).
3. **`make install DESTDIR= PREFIX=/usr`** and **`make uninstall`**: the table in design 11.1.
   - `wps-session` installed as `/usr/bin/wps-session` (from `tools/wps-session`, paths filled in at install).
   - Units and the session file written with installed paths.
4. **Database version:** `PRAGMA user_version` in `service/db.c`.
   - An upgrade runner (steps by number, a `.bak` copy first); 0 → 2 does nothing to the tables (the 0.2 steps add what they need).
   - A newer database is refused with a message.
5. **The first-start step moves into wpsd** (design 2): a versioned marker; the desktop only opens.
   - In 0.2's first steps it still makes what 0.1 made (Templates and System Setup shadows); steps 2–6 add to it.

**Checks:**

- Existing tests all pass from the tree.
- `make install DESTDIR=/tmp/root PREFIX=/usr` gives the expected file list (a test compares it).
- A program run from `/tmp/root` with the overrides starts (headless session test).
- A 0.1 database opens and is marked 2; a "version 99" database is refused.

**(VM):** `git pull && make session`, log in as before: nothing visible changes.

## Step 2. The System folder and the default desktop (M)

1. **`wps/System`:** a folder made at the first start (wpsd).
   - The System Setup folder is moved into it (same ID: its settings objects stay).
   - A Startup folder object for `~/.config/autostart` (step 7 gives it behaviour), and placeholders for Computer, Minimized Window Viewer, LaunchPad and WarpCenter.
2. **The first start** (version 2):
   - On a new desktop: shadows of System, Programs (step 5), Trash Can (step 3) and Templates.
   - On a 0.1 desktop: the System Setup shadow becomes a System shadow; the others are added at free spots.
3. **`WPMinWinViewer`** (WPAbstract, `classes/`): opening it asks the GUI to show the minimized windows (the existing "Minimized windows").

**Checks:**

- A service test makes a new desktop, and one from a 0.1 state; the shadows and folders are as designed.
- A second start changes nothing.
- A deleted shadow is not remade.

**(VM):** the desktop gets System; System Setup is inside it.

## Step 3. Trash Can (M)

1. **`WPTrashCan`** (`classes/WPTrashCan.wpi/.c`): listing of the trash folders (`service/trash.c` reads files/ and info/), rows with origin and date.
   - **Restore:** wpsd moves the item back, with the move job's clash handling.
   - **Delete permanently** and **Empty trash:** a delete job.
   - **Full/empty:** an event when it changes, for its icon.
2. **GUI:**
   - Its menu items carried out by the service (menu ids from the class).
   - The Trash Can's two extra columns in details view.
   - Drops on its icon or window: Delete (no move).
   - Empty and full icons.
3. **On the desktop** by the first start (step 2's list).

**Checks:**

- Service tests T3–T6: trash, list with origin, restore (with a clash), empty (job events), items on a second volume's `.Trash-UID`.
- Headless GUI: drop on the Trash Can trashes; Empty empties after the question; Restore brings a file back.

**(VM):** trash, restore, empty, also with GNOME's Trash open.

## Step 4. Computer, Drives and disk objects (M–L)

1. **wpsd's udisks2 client** (`service/udisks.c`, sd-bus): the ObjectManager's objects (Block, Filesystem, Drive, Encrypted interfaces), and their signals, into a list of volumes; Mount, Unmount, Eject, PowerOff, Unlock calls (asynchronous).
   - Without udisks2: mountinfo only (wpsd's volumes), no mounting.
2. **`WPComputer`**, **`WPDrives`**, **`WPDrive`** (`classes/`):
   - Drives' contents kept in step (central objects by UUID: made, updated, removed).
   - **Opening:** mount if needed, then answer as a folder (`reply_folder` with the mount point).
   - **Menu:** Mount/Unmount/Eject/Power off/Unlock.
   - **Notebook:** properties.
   - **Root:** `/`.
3. **GUI:**
   - Icons by kind and mounted state.
   - Unlock asks for the passphrase (a dialog; the passphrase goes to wpsd, and from it to udisks only).
   - Errors (busy, not authorized) as messages.

**Checks:**

- Service tests against a **fake udisks2** on a private bus (a small Python D-Bus service in `tests/`): a stick plugged and pulled, mount and unmount, a LUKS volume, a busy unmount refused.
- Headless GUI: Drives lists them; opening mounts.

**(VM):** a VirtualBox USB stick or a second virtual disk; mount from Drives, open, eject.

## Step 5. Programs (M)

1. **`WPProgramsFolder`** (`classes/`) and wpsd's keeper (`service/programs.c`):
   - Reads the application folders (as `service/launch.c` already does for file types).
   - Filters NoDisplay, Hidden, OnlyShowIn/NotShowIn.
   - Maps categories to folders.
   - Makes and removes shadows; remembers what it made (by desktop file ID) so the user's deletions stick.
   - Watches the folders (inotify).
2. **On the desktop** by the first start.

**Checks:**

- Service tests: entries in a private `XDG_DATA_DIRS`; one added, removed, hidden, recategorised.
- A shadow the user deleted is not remade.
- The user's own shadow is left alone.

**(VM):** install a program with dnf (or a Flatpak) while WPS runs; it appears in its category.

## Step 6. WarpCenter, first part: the bar (M)

1. **Compositor:**
   - `KIND_PANEL` for `org.wps.WarpCenter`: placed along the first screen's top or bottom edge, full width, above normal windows.
   - The **work area** (the screen less the panel) used by maximize, new-window placement, the desktop's icons area and fullscreen-off.
   - The **input source line** (`I <index> <name>`) and the `keyboard` command (keymap.c).
2. **The bar** (`gui/shell/warpcenter.c`, the desktop process, WPS session only):
   - The Desktop button's menu: the desktop folder, cascades read as they open (svc_list), with Lockup, Shut down and Window list at its end.
   - The Window list button; the keyboard part; the clock with a calendar pop-up.
3. **Meters** (CPU, memory, disk, network from /proc) with the details pop-up.

**Checks:**

- Headless compositor scripts: a maximized window stops at the bar (top and bottom); Super+Space changes the keyboard part.
- The Desktop menu's cascades open the right folders.
- The clock draws.

**(VM):** the bar, the menu, maximize, the keyboard part with Hangul.

## Step 7. Messages and settings objects (M)

1. **The notification service** in the desktop process (`gui/shell/notify.c`, sd-bus): Notify, CloseNotification, GetCapabilities, GetServerInformation; signals back; pop-ups near the bar.
   - "Do not disturb".
2. **`WPMessages`** (`classes/`) and the list window (`gui/shell/messages.c`).
   - Storage in `$XDG_STATE_HOME/wps/messages` (wpsd keeps it, so every GUI sees the same list).
   - The bar's envelope with the unread count.
   - WPS's own status messages also go there (folder windows' status messages after they fade, and the desktop's, which had none).
3. **`WPLaunchPad`** and **`WPWarpCenter`** settings objects (WPSetup subclasses, `classes/WPSetup.c` tables), applied by the desktop.
   - LaunchPad's edge, small icons, text, float on top, shown at start.
   - The WarpCenter's edge and parts.
   - Both shown in a new WPS session.
4. **Startup** (design 7.1):
   - Drops into Startup make autostart entries (programs, scripts) or shadows (other objects).
   - The desktop opens the shadows at login.
   - "Start at login" check box for entries.

**Checks:**

- `notify-send` in a headless session gives a pop-up and a count; an action button reaches the program (a test client listening for ActionInvoked).
- Messages kept across a restart.
- Settings change the bar's edge live.
- Startup: an entry made from a drop runs at the next (headless) start; a shadowed folder opens.

**(VM):** notifications from programs (e.g. a download in Firefox), the Messages list, moving the bar to the top, a program in Startup.

## Step 8. WarpCenter tray (M–L; may move to 0.3)

1. **StatusNotifierWatcher and host** (`gui/shell/tray.c`): `org.kde.StatusNotifierWatcher` on the session bus; items' properties (IconName, IconPixmap, ToolTip, Status) and signals; Activate, SecondaryActivate, ContextMenu.
2. **dbusmenu client:** the item's menu (`com.canonical.dbusmenu` GetLayout, Event) drawn as a WPS menu.

**Checks:** a test item (Python, on a private bus) shows, changes icon, opens its menu, receives the click.

**(VM):** a program with a tray icon (e.g. an AppIndicator test, or nm-applet if used).

**Decision point:** if steps 1–7 run long, this step moves to 0.3 and 0.2 ships without the tray (the bar keeps room for it).

## Step 9. The RPM and the release (M)

1. **`packaging/wps.spec`** and **`make dist`** (a tarball with `VERSION` in its name).
   - Subpackages `wps` and `wps-gnome-shell-extension`.
   - BuildRequires and Requires as in design 11.3.
2. **Built** with `rpmbuild` and in **mock** (fedora-45-x86_64).
   - `rpmlint` clean, or each warning explained.
3. **COPR:** the project and its build from the tag (needs the owner's Fedora account; the owner creates the project, the spec and instructions come from here).
4. **A fresh Fedora 45 VM:**
   - `dnf install wps`; log in to WPS: the default desktop (System, Programs, Trash Can), WarpCenter, LaunchPad.
   - Log in to GNOME; upgrade to a newer build; `dnf remove`.
5. **Version 0.2.0:** `VERSION`, roadmap and README updated, tag `v0.2`, release notes, the RPMs attached to the GitHub release.

**(VM):** the install itself, on a clean machine.

## Order and checkpoints

| Step | Depends on | Owner's check |
|---|---|---|
| 1 Groundwork | (none) | nothing changes |
| 2 System folder | 1 | System on the desktop |
| 3 Trash Can | 2 | trash, restore, empty |
| 4 Drives | 2 | a USB stick |
| 5 Programs | 2 | a newly installed program |
| 6 WarpCenter bar | 1 | the bar, menu, keyboard |
| 7 Messages, settings, Startup | 6 | notifications, notebooks |
| 8 Tray | 6 | a tray icon (or moved to 0.3) |
| 9 RPM and release | all | install on a clean VM |

**Order:**

- Steps 3, 4 and 5 are independent of each other; step 6 can start after step 1 in parallel with them.
- The order above is the suggested one: what is seen on the desktop first, then the bar, then packaging.

## Risks

- **udisks2 and polkit:** mounting internal partitions needs an administrator's password through polkit; there is no polkit agent in the WPS session yet. **Mitigation:** a minimal polkit agent in the desktop process (step 4, an extra M if needed), or removable media only in 0.2.
- **Notifications:** programs may expect GNOME's extras (sound, images in bodies). **Mitigation:** advertise only the capabilities implemented; programs fall back.
- **The tray:** dbusmenu menus vary a lot between programs. **Mitigation:** step 8 can move to 0.3.
- **Packaging dependencies:** wlroots 0.20 and glycin as Fedora 45 packages; if a dependency is not packaged, it is built in the COPR project too.
- **Upgrading 0.1 users:** only the owner's machines have 0.1. The upgrade path is still tested (step 1, step 2), since later versions need it.
