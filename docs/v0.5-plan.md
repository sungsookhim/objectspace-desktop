# Version 0.5 implementation plan: ready to be public

2026-11-24, for the roadmap's 0.5 ([roadmap.md](roadmap.md), "Proposed order") and the names chosen in [v0.5-names.md](v0.5-names.md). The project becomes **Objectspace** (Objectspace Desktop), in the repository `sungsookhim/objectspace-desktop`, and opens to the public when 0.5 is done. 0.5 adds no features.

**How to read it:**

- Steps in order; each ends with the tree building, its suites green, committed and pushed.
- **(VM)** marks a step the owner tries on the VM. A clean break: remove 0.4.1 (`sudo dnf remove wps wps-gnome-shell-extension wps-devel`, the folders `~/.config/wps`, `~/.local/share/wps`, `~/.local/state/wps`), then install the new build.
- The renames are made by a script, `tools/rename-0.5.py`, from the tables in [v0.5-names.md](v0.5-names.md): reviewable as a table, repeatable, and each step's diff only what the script did plus the fixes after it.
- The step-by-step history (0.1 to 0.4.1 plans, notes, reviews) is not renamed: it is the record of what was.

## Step 1. The rename tool (S)

1. `tools/rename-0.5.py`: maps of whole words (classes, methods, macros, commands, IDs, paths) and of file names, applied with word boundaries, to the tree's code, build files, tests and current documents; it prints what it changed and what it skipped. A `--check` mode lists every old name left (the release's check).
2. A list of what it never touches: `docs/v0.[1-4]*`, `docs/notes`, `docs/reviews`, `docs/release-notes-0.*`, the history parts of `docs/roadmap.md`.

**Checks:** the tool's own test (a small tree renamed and checked); `--check` on today's tree reports the counts of [v0.5-names.md](v0.5-names.md).

## Step 2. The code's own names (L)

Tier 3 and the classes, all internal or SDK, one mechanical pass:

1. Classes `WP*` to `Osd*` (`WPObject` to `OsdObject`, `WPWarpCenter` to `OsdTheBar`, `WPLaunchPad` to `OsdLauncher`, `WPMinWinViewer` to `OsdMinWinViewer`, ...); methods `wp…`/`wpcls…` to `osd…`/`osdcls…`; the `.wpi` files to `.osdi` and the class compiler `wpoc` to `osdc`.
2. The runtime `wpo_` to `osdo_`; `wps_` to `osd_`; `WPS_` macros to `OSD_`; header guards, menu IDs.
3. File names: `classes/WP*.wpi`, `wps_*.c`, `service/wpsd*.c`, `gui/shell/warpcenter.c` (thebar.c), `launchpad.c` (launcher.c).

**Checks:** `make check`, `gui-test`, `comp-test`, the golden self-tests (their expected lines renamed by the tool too); the plug-in SDK's sample built against the new names.

## Step 3. What other programs and users see (M) (VM)

1. Commands: `osd`, `osdctl`, `osd-shell`, `osd-terminal`, `osd-session` with their long names as links (`objectspace`, `objectspace-ctl`, ...); `libexec/objectspace/osdd`, `osd-watchd`, `osd-plughost`, `osd-compositor`. Manual pages under both names.
2. Packages `objectspace`, `objectspace-devel`, `objectspace-gnome-shell-extension`; systemd units (`osdd.service`, `osd-watchd.service`, `osd-session.target`); PAM `osd-lock`; the session on the login screen, **Objectspace**.
3. App IDs `io.github.sungsookhim.Objectspace.*`; the GNOME extension `objectspace@sungsookhim.github.io` and its schema.
4. On disk: `~/.config/objectspace`, `~/.local/share/objectspace`, `~/.local/state/objectspace`, `/usr/share/objectspace`, `/usr/lib64/objectspace`; the socket `objectspace.sock`; attributes `user.osd.*`; files `.osdicon`, `.osdobj`; the environment `OSD_*` (`OSD_FOLDER`, `OSD_OBJECT`, ...).

**Checks:** the suites; the RPMs built in mock and installed on a clean VM (the owner's), the session from the login screen, and inside GNOME.

## Step 4. What the user reads (S-M) (VM)

1. **TheBar** and **Launcher** in every title, menu, notebook and System Setup object; the terminal is **Objectspace Terminal**; the icon themes **Objectspace (flat)**, **Objectspace (outline)**, Classic.
2. No "OS/2", "Warp" or "WPS" in what the program shows (menus, dialogs, notebooks, messages, About); comments keep OS/2 only where they explain where an idea comes from, "WPS" nowhere as this project's name.
3. Current documents (README, the design documents in use, the SDK's README, the manual pages) in the new names.

**Checks:** `rename-0.5.py --check` finds no old name outside the history; a headless screenshot of every window with text checked by eye.

**Added after step 4 (the owner's ask):** a **Command Prompt** object in My System (class `OsdCommandPrompt`, first-start step 12, one of Restore Desktop's defaults): the user's shell in the System's terminal, in the home folder or the folder its Program page's "Start in" names. `osdctl open` now passes its display, as `osd` does. Test: `tests/comp/terminal-programs.sh`.

## Step 5. What is in the repository (S-M)

1. An SPDX line (`SPDX-License-Identifier: MIT`) and the copyright on every source file; `NOTICE` for third parties (the Wayland protocol files in `proto/` and their licences; the libraries linked dynamically, none copied in).
2. **The pictures and sounds:** each icon traced to its maker (the isometric set: `tools/icons/make_iso.py`; Classic: 0.2's, drawn here), recorded in `data/icons/README.md`.
3. **The history:** `docs/HISTORY.md` and a note at the top of the README: up to 0.4.1 the project was private and named WPS (a Workplace Shell for Linux); 0.5, the first public version, took its own name, Objectspace, for that reason. The old documents stay as they were, under that note.
4. A last search of the history for anything private (done once: nothing but the owner's GitHub name and e-mail).

**Done** (2026-11-24): the lines on every file that takes comments (`tools/spdx.py`; `make check` checks them; files without comments, such as pictures, JSON and Markdown, are covered by `NOTICE`); `NOTICE` gives the protocol files' notices (generated at build time; nothing else from other projects is in the tree) and the trademark notice, and the RPM installs it; `data/icons/README.md`; `docs/HISTORY.md` and the README's note. The search of the history found the owner's name and e-mail, the machine name "HomeLinux" in six commits' author name, and a link to a private Claude doc in the README (to go in step 6's README); nothing else.

## Step 6. For people who come to it (M)

1. **README** for strangers: what Objectspace is (and that it is inspired by OS/2's Workplace Shell, with the trademark notice: OS/2 and Workplace Shell are IBM's; no affiliation), screenshots, installing, building from source, the status, the authorship note (designed by the owner, code written with Claude through Claude Code).
2. **CONTRIBUTING** (building, the tests, the code's style, the design documents' role), **CODE_OF_CONDUCT**, **SECURITY** (how to report), issue and pull request templates.
3. **Continuous integration:** GitHub Actions on Fedora 45 (a container): the build, `make check`, `gui-test`, and the compositor's headless tests where the runner allows.

**Checks:** a run of the workflow green on a branch.

## Step 7. The release, 0.5.0 (S)

`VERSION` 0.5.0; the release notes (what changed: the names; nothing new besides); the RPMs in mock, `rpmlint`; a clean install on the VM (the owner's); a draft GitHub release for the owner's check, then published (tag `v0.5.0`); **the repository made public** (the owner's, when ready).

## Order and risks

- Step 2 before 3: the code's names first, so step 3 changes only what is seen outside, and each step's suites tell what broke.
- **The rename is mechanical but wide** (about 400 files): done by the tool, never by hand, so a mistake is fixed in the table and the tool run again from the step's start.
- **Word boundaries:** short names (`wps`, `wpo`) appear inside other words; the tool matches whole identifiers and checks its own result (`--check`), and the compiler finds what it missed.
- **The golden files and baselines** change with the names: taken again after step 4, said in its commit.
