# Version 0.4 implementation plan

2026-11-22, for [v0.4-design.md](v0.4-design.md). **Rebuilt on the object-property base** (the refactor, [object-properties-design.md](object-properties-design.md), stages R0-R6, merged at a657bd4): what 0.4 adds is declared as properties, so each step gets its notebook fields, setup strings, Class... (all of a class or a type), Default, actions and plug-in access with no code of its own.

**How to read it:**

- Steps in order; each ends usable, tested and pushed, and the owner tries it on the VM where marked **(VM)**, with `git pull && make session`.
- Sizes are relative (S, M, L), as in the roadmap; most are smaller than in the first draft, the properties' part being done.
- Every step keeps the refactor's checks: `make check` (with tests/props and tests/plugins), `gui-test`, `comp-test`, `visual-check`, the golden self-tests. A change of looks on purpose takes a new visual baseline, said in its commit.
- Grouped so that each step works in one part of the code: icons (2, 3), folder windows (4, 5), objects (6), palettes (7, 8), work areas (9, 10).

## Step 1. Groundwork (S)

1. `VERSION` 0.4.0-dev; `WPS_PROTOCOL` 3 (the refactor's ops: get, set, props, reset, scope targets).
2. **librsvg** as a build and run dependency; the RPM's new requirements (Pillow, zlib, librsvg, and the `wps-devel` subpackage) built in mock.
3. **Carried fixes** (design 12): Open With's list on a worker; a left-side drawer's cascade opening to the left; M4 scenario 38 and the two-window drag self-test, fixed or explained.
4. **From the refactor (design 7, carried on):** a folder's sort and columns made plain stored properties (moved from WPFolder's older storage once), so Class... sets them for all folders.

**Checks:** the above; a mock build; the drawer cascade headless; tests/props: `class:WPFolder` sort and columns.

## Step 2. Icon themes (M) (VM)

1. **wpsicon in the window:** `icons.c` loads packages (and plain pictures) through `wpsicon.c`, renders the size asked (device pixels) with a cache by (package, size); the SVG through librsvg.
2. **The theme is a property:** `icon_theme` (a choice, its options the installed and the user's themes: an `options` method), declared on WPObject: the System notebook's Icons page edits `class:WPObject`'s (every object), and any folder or class can have its own through the chain (design 2.3). Default WPS (flat). A change redraws every window, the LaunchPad, the WarpCenter, menus (`defaults_changed`).
3. **Names:** wpsd's listings say `theme:NAME` for WPS's own objects and data files by type (design 2); the window resolves them (theme, then wps-flat, then the drawn kind). The system buttons (WarpCenter, LaunchPad) from the theme.
4. **Choose...** on the Icon page takes `.wpsicon` packages, and unpacks `.ico` and `.icns` into packages.

**Checks:** unit tests for the type-to-name table and the theme lookup (a missing name falling back); headless: the desktop drawn with each theme; a theme switched live; one folder with a theme of its own.

## Step 3. Icon sizes and the open icon (M) (VM)

1. **The icon set is a property:** `icon_set` (Small 32/16/16, Default 64/32/16, Large 96/48/24; the owner's), on WPObject like the theme: the System's for all, a folder's own possible. The toolkit's metrics from the set (`ICON 32`, `UI_CELL_W`, menu rows, the LaunchPad's buttons: one metrics structure), so cells, layout, hit tests, menus and the LaunchPad follow it live.
2. **The open icon:** the theme's `NAME-open` for special folders; an object's own as a property (`icon_open`, the Icon page's **Open** field); shown while open (the in-use state wpsd sends).
3. Sizes through wpsicon's rules: an exact size first, then the rules (the owner's).

**Checks:** headless: the three sets at scales 1 and 2 (no overlaps; menus and the LaunchPad at the set's sizes); a folder's icon changing to its open one while its window is open. Looks change on purpose: a new visual baseline for Default (64).

**As built (2026-11-23):** `ui_icon_set` in the toolkit (the System's, `ui_icons()`; a container's own); cells `max(100, L+48)` by `L+48` (Small's is 0.3's 100 by 80). Icon positions are stored in Small's units and shown in the folder's set's, so an arrangement keeps its shape when the size changes (the desktop keeps them on the screen). Like `icon_theme`, `icon_set` is WPFolder's (the System's edits `class:WPFolder`). The tests: `tests/comp/icon-sizes.sh` (`SCALE=2` for a scale of 2). After the owner's look: the System's page named **Theme**; the Icon page's **Base icon**, **Open icon** and **Hatched while open** (`open_hatch`: the hatching behind the open icon too; the System's Theme page **Hatch open icons too** for every object); an object hatched while its Properties notebook is open (its base icon); the hatching twice as wide and as far apart from 48 pixels. Left for later: the title bars' icon (a drawn glyph), the LaunchPad drawers' rows (24), the desktop entries' icons (their 64 PNG), an own open icon copied as the normal one is (it is kept as the path chosen).

## Step 4. OS/2's free icon layout (M) (VM)

1. `layout.c`: per-item widths beside 0.3's heights; free packing (rows to the window's width, as tall as their tallest); Arrange and Sort in it; locked icons kept.
2. The container: hit tests, drawing and title wrapping at each item's width.
3. **`layout` (grid or free) is a folder property** on its Icon view page: all folders' through Class..., one folder's own.
4. **Where icons start** (the owner's, 2026-11-23), in both layouts: a big folder opens at its first icons, top left, and in name order (today it follows the directory's order while the names are not all read: the service's sorted listing for the first arrange); with the window's remembered size and position (step 5), its scroll position kept too, or the top. (Fixed now: icons laid out before their names were read moved below all the others at the next full layout, leaving the top of /usr/bin empty.)

**Checks:** unit tests (`test_layout`: widths, packing, locked icons); headless: a folder of long and short titles in free layout; a folder of 3000 opened: its first icons at the top, by name.

**As built (2026-11-23; the owner's choices: free is the default layout, Sort by name the default sort):** `layout.c`'s free mode: per-item widths (`ui_icon_cell_width`: the widest title line + 12, between the icon + 16 and four icons), the spots flowed in order to the width taken with the columns (a resize moves nothing; Arrange takes the window's), wrapping into rows as tall as their tallest, clear of placed icons; an emptied spot keeps its width; the flow worked out again from the row of the first spot that changed. The container takes each item's width (`item_w`) for drawing, hit tests and the two-line titles. `icon_layout` (free, grid) on WPFolder's Icon view page; a change arranges the folder. WPFolder's `sort_key` defaults to name (folders first): wpsd lists a folder in that order, so a big folder opens at the top in name order with no names read by the window; Arrange follows the folder's sort (by name client-side only when its sort is none), and the first arrangement waits for the folder's properties. Cost: a sorted folder is read again whole when its contents change (as a sorted one was in 0.3). Not done: free rows keep a two-line title's room (rows of one-line titles could be shorter); the scroll position with the remembered window (step 5).

**After the owner's look (2026-11-23):** a scroll bar's arrow or trough held repeats (after 400 ms, every 60 ms; the trough pages until the thumb is under the pointer, which may move meanwhile; a click is still one step). A pop-up menu's object is outlined while the menu is open (OS/2's source emphasis): a dotted black-and-white rectangle round the icon's cell (and round the selection's, when the icon clicked is part of it: the menu is for all of them), inside the folder's area for the folder's own menu, round the desktop for the desktop's. A title change re-flows the free layout (a title's width is its cell's). Test: `tests/comp/menu-emphasis.sh`.

## Step 5. Folder windows and the desktop's messages (M) (VM)

1. **Folder windows remember** their place, size and view: properties with no field (`win_place`, `win_size`, `win_view`), kept per user; the WPS session places them through the compositor; inside GNOME size and view (the extension's `place`, if it can).
2. **The search field's place:** a property (top, bottom, floating), on folders' View page and for all of them through Class....
3. **The resize pointer** on column edges.
4. **The desktop's status line:** a transient box above the WarpCenter; action problems (now in Messages) shown there briefly too.
5. **Positions from 0.2:** the status line's Arrange offer, once.

**Checks:** headless (WPS session): a folder closed and opened again at the same place and size; the search field at the bottom; a message shown on the desktop; the cursor shape over a column edge.

**As built (2026-11-23):** (1) Each view's window is kept on the folder, per user, as properties with no field: `win_icon`, `win_details`, `win_tree` ("x,y,w,h,maximized,scroll"; x -1 where the place is not known, as inside GNOME) and `win_view`, the view last closed (what a plain Open, a double click or the LaunchPad opens: `VIEW_LAST`; Open ▸ Icon/Details/Tree open that view). `open_folder` reads them first (the window comes after one round trip; a second click meanwhile is not a second window), then the size, the compositor's `place` in the WPS session, maximized, and the scroll once the contents are in (again when the stored positions come). The command line, restoring at login and the self-tests open at once (`open_window`). Saved when the window closes. A window made narrower comes back flowed to its width (the free layout's rule). (2) WPFolder's **Search field (Ctrl+F)**: top, bottom (over the status line), floating (a box over the list's lower right; the container's overlay, drawn with the list and kept in place as it scrolls). (3) `col-resize` over a column's edge (a surface's client pointer, kept by the frame; `sb_h_double_arrow` for older themes). (4) The desktop's messages in a box at the bottom of its usable area: 5 s, an error until clicked (by its words: failed, cannot, ...); shown again only for a new message (`set_status`: always); wpsd's "An action was not done" from Messages shown there for a moment. (5) Placed icons over each other (more than 4 px): the status line offers **Arrange** (a link; on the desktop, in its box), once per folder (`arrange_offered`); nothing moves unasked. Found on the way: wpsd freed a client's subscriptions while sending an event through them (a client gone as a folder's window settings were saved); a failed send now marks the client and the loop closes it (`drop` in wpsd.c). Tests: `tests/comp/folder-window.sh`, `search-place.sh`, `desktop-status.sh`, `arrange-offer.sh`, the pointer in `details.sh`. After the owner's look: the desktop shows outcomes only (work under way, "Moving 2 of 5", "Emptying the trash...", is the folder windows' status lines'); the Messages object's **Show WPS's messages at the bottom of the desktop** (`desktop_line`, on) turns them off; `wpsctl say [--stay] TEXT` (op `say`, the event `say` to every client) shows a script's or a timer's message there, with the setting off too; a template dropped says "Making 1 new object...", not "Moving". Known, not from this step: golden `newfolder` now and then gives two Data Files made at once each other's drop position (a race of two drops; about 1 in 4); the visual shots' desktop row differs between runs (the first start's icon order).

## Step 6. Objects and programs (M) (VM)

1. **Prevent delete:** a WPObject property (`no_delete`, the General page): wpsd refuses delete, trash and Trash Can drops; WPS's own objects get it at the first start (a new first-start step: `set` on them).
2. **Extension change on rename:** the dialog (Use / Keep / Cancel) when extensions are shown.
3. **A shadow's menu is its original's:** wpsd's `menu` for a shadow builds the target's, then the shadow's items.
4. **Executables' Program page** (design 8): its properties declared on data files that are programs; wpsd's `open` follows them.
5. **Activation tokens:** the window asks for one (`xdg_activation_v1`) and sends it with `open`; wpsd sets `XDG_ACTIVATION_TOKEN` and `DESKTOP_STARTUP_ID` (for run: actions too).

**Checks:** wpsd tests (delete refused; the shadow's menu; an executable opened by its page's settings; the token in the program's environment); headless: the rename dialog.

**As built (2026-11-23):** (1) WPObject's `no_delete` (General page, **Prevent delete**): wpsd refuses trash and delete jobs holding such an object (the whole selection: nothing goes; "all" walked by `wps_selection_each`), a move into the Trash Can, `vtrash`/`vdelete`/`vmove` into the Trash Can of central objects, with an error `protected` naming it (a shadow by its original's title); the GUI shows "Cannot trash: ..." (on the desktop: until clicked). First-start step 11 (`FIRST_START_VERSION` 11) and Restore Desktop put it on WPS's folders (System, System Setup, Programs, the Trash Can, Templates, Startup, Computer, Drives), the noted default objects and the settings objects; each shadow the first start makes gets it as it is made. (2) With extensions shown, a rename to another extension (or none) asks: **Use .md / Keep .txt** (the new name with the old extension) **/ Cancel**. (3) wpsd's menu for a shadow is its original's (Open's views or programs, Arrange, Empty trash, a plug-in's items), then the shadow's own items it lacks; `menu_select` goes to the original first. Arrange on a folder's icon (or a shadow of one) arranges that folder (its open window, else wpsd's `arrange`), no longer the window it is in. (4) WPDataFile's `prog_cwd`, `prog_type`, `prog_close` on a **Program** page shown for programs (`wpQueryIsProgram`, the `wps_is_program` hook: ELF or #!); `open` follows them (automatic: as before). (5) `open_req` waits for an xdg-activation token (`ui_activation_token`: the last input's serial, the focused surface) and sends it as `token_env`; wpsd gives the program, and the open's `run:` actions, `XDG_ACTIVATION_TOKEN` and `DESKTOP_STARTUP_ID` (not kept for the client's later actions). A script run in a terminal: the terminal gets it. Tests: `tests/firststart` (Prevent delete, the shadow's menu), `tests/programs` (the Program page, the token), `tests/comp/rename-ext.sh`, `activation.sh`.

## Step 9. Work Area folders, part 1: the group (M-L) (VM)

1. **The setting:** `work_area`, a folder property (its File page).
2. **wpsd:** objects opened from a work area (or from a folder or shadow in it) recorded as its group, with their scopes; the group's state kept at logout. Its events (`work_area.open`, `work_area.close`) declared: actions can follow them.
3. **The compositor:** a scope's processes linked to their windows (Wayland client PID; X11 `_NET_WM_PID`); a group's minimize, restore, close.
4. **The folder's window:** minimizing, restoring and closing it act on the group (WPS session).

**Checks:** headless (WPS session): two test programs opened from a work area folder, minimized and restored with it, closed with it.

## Risks

- **Icon size** touches every place a 32 px icon is assumed (cells, menus, the LaunchPad, drag images): step 3 gathers them into one metrics structure first.
- **librsvg** in the window process: SVGs are drawn on the UI thread when first needed; a large or broken SVG must not stall it (a size limit; drawn once per size and cached).
- **Work areas** depend on linking processes to windows: programs that hand their window to an instance already running (most GNOME apps, Firefox) belong to the first instance's group only. The design accepts that; the status line says so when it happens.
- **Window placement inside GNOME** depends on the extension.
- **Protocol 3:** the number is reported by ping (and wpsctl); nothing refuses an older GUI yet - after an upgrade, logging out and in again starts both anew.
