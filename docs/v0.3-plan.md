# Version 0.3 implementation plan

Draft, 2026-11-21, for [v0.3-design.md](v0.3-design.md).

**How to read it:**

- Steps in order; each ends usable, tested and pushed, and the owner tries it on the VM where marked **(VM)**, from the RPM (`make srpm`, built in mock) or with `git pull && make session`.
- Sizes are relative (S, M, L) as in the roadmap.
- The owner's two ideas after 0.2 come first (steps 2 and 3), then the folder work, then programs, then the larger pieces. Work Area folders moved to 0.4 (the owner's, 2026-11-21).

## Step 1. Groundwork (S–M)

1. `VERSION` 0.3.0-dev.
2. **Two field kinds** for notebook pages (design 1): `file` (Browse..., a filter by type, a picture preview) and `color` (a swatch and a picker), in `gui/ui_notebook.c` and the page parser in `wps-shell.c`.
3. **Shared session code** (`gui/shell/session.c`): Lockup, the end-session dialog, Log off, from the WarpCenter's code; the WarpCenter uses it.
4. **Carried from 0.2** (design 13): the first start's extra icon (a headless first start, recorded); manual pages for `wpsctl`, `wps-shell`, `wps-session` (in the RPM); confirmations from the System object; Delete in tree view on the whole selection.

**Checks:** unit tests for the field parser; a notebook self-test with both new kinds; the WarpCenter's Lockup and Shut down unchanged (headless); `rpmlint` without the man-page warnings.

**As built:**

- Field kinds `file` (a path, Browse..., drops; the page's choices give the kind, `image` or `audio`) and `color` (a swatch, `#rrggbb`; a bad value put back). Browse... opens `gui/shell/filepick.c`: folders first, then files of the kind, pictures with previews, Up and a path field. Self-test `fields`.
- `gui/shell/session.c`: Lockup, Shut down and Log off for the WarpCenter and LaunchPad; `tests/comp/session.sh` (7 checks).
- Man pages in `data/man`, installed by `make install` and the RPM.
- Delete in tree view acts on the whole selection, one job per folder; the tree self-test covers it.
- Confirmations already came from the System object; only a comment was out of date.
- The first start's extra icon: not reproduced headless (self-test `first`); in [open-issues.md](open-issues.md).

## Step 2. The desktop's menu (S) (VM)

1. **System setup** ▸ (the System Setup folder's objects, read when the menu opens), **Lockup now**, **Shut down...** on the desktop's background menu (design 2), in both modes.
2. Inside GNOME: Lockup through `org.gnome.ScreenSaver`, Shut down through `org.gnome.SessionManager`.

## Step 3. Backgrounds (M) (VM)

1. **Background page** on WPFolder: image (file), display (normal, tiled, scaled, stretched), colour; **Use GNOME's background** on the desktop's (design 3).
2. `wallpaper.c` generalised: a decode cache by path and size; the desktop draws its own choice when GNOME's is off.
3. Folder windows draw their background.
4. Stored in the folder's state.

**Checks:** a headless desktop with an image set (pixel check at the corners and centre for each display mode); a folder window with a colour; GNOME's background still followed with the checkbox on; the setting survives a restart.

**Decided:** the desktop's page does not write GNOME's setting (the owner's).

**As built:** WPFolder's Background page (`bg_image` a file field taking pictures, `bg_mode` centred/tiled/scaled to fill/scaled to fit/stretched, `bg_color`, and on the desktop's `bg_gnome`, on by default); wpsd tells the class which folder is the desktop (`wps_is_desktop`, from its first start). The desktop draws its own through `wallpaper_own` (GNOME's settings untouched); folder windows draw theirs through `ui_container_set_background`, behind the items in content coordinates (the picture on the first screenful, tiled everywhere; titles on a picture as on the desktop). Each window follows its folder object (a subscription to it). A colour field emptied means none. `tests/comp/background.sh` (6 checks).

## Step 4. Details view: sorting and columns (L) (VM)

1. **wpsd:** `list` takes `sort` (key, direction); a per-folder sorted index built on a worker (`service/listing.c`), folders first; patched on inserts and removes, rebuilt for batches.
2. **The folder's Sort page:** key, direction, Always maintain sort order (today's `sort_order` brought along).
3. **The details view:** clicking a heading sorts (again: reversed), an arrow on it; column widths dragged, kept per folder.
4. **Columns:** the folder's Details view page and the System object's default (design 4).
5. The icon view's Sort and Always maintain use the same order.

**Checks:** unit tests for every key and direction, folders first, patches, a 100 000-entry folder sorted within a bound; a headless details view: heading click order, reverse, a column hidden, widths kept after reopening.

**As built:**

- **Sorting in wpsd's listing** (`service/listing.c`): a folder with a sort (`sort_key` 0 name, 1 type, 2 size, 3 last write; `sort_desc`) is read whole, sorted on the worker (folders first, either way; central objects by their titles) and paged in that order. Additions and renames mark it stale, so windows read it again (removals follow by position); the windows' models stay positions in the listing, unchanged. Without a sort (the default), listings stream as before. The sort comes from the folder's object in memory (its state may not be written yet).
- **The folder's pages:** View has Sort by (none, name, type, size, last write) and Descending; a new Details view page turns Real name, Type, Size and Last write on and off; the widths are a hidden setting.
- **The details view:** headings Title, Real name, Type (Folder, Program, or the extension), Size, Last write; a click sorts the folder (again: reversed), an arrow shows the sort; a column's edge dragged sets its width, kept by the folder. Every window on the folder follows (it reads the folder's settings on each change).
- **Not done:** Always maintain sort order for the icon view (its Sort menu arranges, as before); Last access, Created and Class columns; the 100 000-entry bound (a sorted folder is read whole before its first page: fine for folders of thousands, slow for a million).
- `tests/sort` (11 checks), `tests/comp/details.sh` (6 checks).

## Step 5. The search field; hidden files (M) (VM)

1. **wpsd:** `list` takes `filter` (text matched against names and titles); paged.
2. **The search field** at the top of folder windows; Ctrl+F there, Ctrl+Shift+F for Find; Esc clears.
3. **Hidden files:** lock files never listed; dot files shown or hidden by **Show hidden files** in the System object (one system choice; starts as shown).

**Checks:** unit tests for filters and hidden rules; a headless window filtered live and cleared; hidden files shown and hidden by the setting.

**Decided:** one system choice in the System object, starting as shown (the owner's).

**As built:**

- **Decided** (the owner's): the field shows only when needed, with Ctrl+F, under the title bar; typing in the folder still jumps to a name (type-ahead); Find... is Ctrl+Shift+F. Later: a setting for where the field sits (top, bottom, floating). Mock-up: [mockups/0.3-search-field.png](mockups/0.3-search-field.png).
- **wpsd:** `list` takes `filter` and `hidden`; such a listing is the window's own (keyed by folder, filter and hidden), read whole and read again on any change in the folder. Lock files are never listed, nor sent as changes.
- **The window:** Ctrl+F shows the row (magnifier, Find:, the field, x) and focuses it; each key filters (its own listing); Enter, Down or Tab go to the objects with the filter kept; Escape or x take the row away and all come back. While filtered, icons flow from the top left in name order and no spot is stored; cleared, they are back in their places. The status line says how many match.
- **Show hidden files** in the System object (Folders page; on by default): every window lists again when it changes.
- `tests/sort` (7 more checks), `tests/comp/search.sh` (4 checks), self-test `search`.

## Step 6. Icon view: OS/2's layout, locked positions (M) (VM)

1. **Whole titles**, rows as tall as their tallest title; the folder's Icon view page chooses whole or two lines (design 5).
2. **Lock position** on objects' menus and General page; **Lock positions of all icons** per folder; the flag stored with the position.
3. Arrange and Sort flow around locked icons.

**Checks:** a headless layout with long titles (row heights, no overlaps); a locked icon dragged within its folder stays, dragged onto a folder moves; Arrange leaves it.

**Decided:** a locked icon can still be dragged to other folders and objects (the owner's).

**As built:**

- **The layout** (`layout.c`): each icon's cell is as tall as its whole title (`ui_icon_cell_height`, up to 12 lines); a grid row is as tall as its tallest cell, and the rows below move down. Spots are handed out in order, clear of placed icons. Titles are measured once per title (cached in the window's rows).
- **The folder's Icon view page** (new): **Titles** whole (the default, desktop too) or two lines (as before: the whole title over the neighbours when selected); **Lock positions of all icons**.
- **Lock position:** a check item on an icon's menu in icon view (all the selected ones with it), and a checkbox on its **General** page (when its folder is loaded, i.e. open). Stored with the position in the folder: `pos:ID = "x,y,L"` (`"L"` alone: locked from the notebook before a position was stored; the window stores where it is). `place` takes `lock`; `layout` replies `locked`; `arrange` keeps locked positions.
- **Dragging** a locked icon within its folder leaves it ("The position is locked" in the status line); the others selected with it move. Onto other folders and objects it goes as before. With all locked, Arrange and Sort say so and do nothing.
- Positions stored before 0.3 (two-line rows) may overlap long titles until Arrange.
- `tests/test_layout` (2 more tests), `tests/sort` (8 more checks), self-test `layout`.

## Step 7. Open With and program settings (M) (VM)

1. **Open** ▸ on data files: the default program, the other programs for the type, Other program... with Always use for this type (`mimeapps.list`) (design 7).
2. **Program page:** Program type, Close window on exit, Working directory; the **Terminal** choice in the System object; the **Association** page (design 8).
3. Programs opened through Open With are tracked (in-use emphasis).

**Checks:** unit tests for the program list per type (desktop entries and `mimeapps.list` in a scratch `XDG_DATA_DIRS`), the terminal choice and the hold option; a headless Open ▸ with two programs; a text-mode program kept open after exit with the checkbox off.

**As built:**

- **Open ▸** on a data file (not an executable): wpsd adds the cascade to the menu (`WPS_MI_OPEN_APP` + k, the default checked, as OS/2 marked the default view), then **Other program...**. The list: the type's default, `mimeapps.list`'s added associations, the user's own desktop entries that name the type, `mimeinfo.cache`'s, then the same for its parent types (`mime/subclasses`: a text editor for C files). A double-click still opens with the default.
- **Other program...** (`gui/shell/apppick.c`): every installed application by name (`apps` op; hidden ones left out), **Always use for this type** (the user's `mimeapps.list`: the default and first among the added; GNOME reads the same). `open` takes `app` or `app_index`, and `always`. Programs opened so are tracked (in-use emphasis).
- **The Program page:** Working directory (`~` allowed; gone: home), **Program type** (automatic: the entry's `Terminal` key; window; text mode), **Close window on exit (text mode)** (off: `sh -c` waits for Enter after it ends, with any terminal). Kept in WPS's state, not the entry.
- **The System object's Programs page:** **Terminal for text-mode programs** (automatic, or one of the known terminals; one not installed falls back to the first installed) and **Or this command**. `WPS_TERMINAL` is still read when no command is set. wpsd reads the System object at start and follows its changes.
- **The Association page** (programs from desktop entries): the types it opens; a change writes the user's copy of the entry (`~/.local/share/applications`, GNOME sees it).
- Not in this step: a Program page for executable files (they keep today's guess).
- Fixed on the way: MIME globs marked case-sensitive are tried first in the name's own case (`prog.c` was taken for C++ by `*.C`).
- `tests/openwith` (20 checks, in `make test`), self-test `openwith`.

## Step 8. Templates (S–M) (VM)

1. **New** ▸ on background menus (design 9).
2. **Create another** ▸ asks for a name and folder.
3. Shift+drag moves a template; a plain drag makes an object.
4. New data files' titles without the extension.

**Checks:** a headless New ▸ making each built-in template at the click's spot; Create another into another folder; a Shift+drag moving a template.

**As built:**

- **New ▸** on every folder's background menu and the desktop's: the Templates folder's templates by title (read when the menu opens); the object is made at the click's spot (icon view), its name ready to edit.
- **Create another** asks the name in a dialog with **Folder...** (the file picker's new folder mode, **Use this folder**); on a template it makes an object from the template.
- **Templates dragged:** a plain drag makes a new object, within the template's own folder too; **Shift+drag** moves the template itself (and repositions it in its folder).
- **Decided** (the owner's): extensions are hidden by a System choice, **Show file extensions in titles** (Folders page, on by default), not per new object. Off: data files' icons are titled without the extension (`.tar.gz` as one); renaming keeps the file's extension ("x.txt" typed for x.odt gives x.txt.odt, as elsewhere with hidden extensions); folders, programs and objects with titles of their own are unchanged; the details view's Real name shows the whole name.
- The owner asked about type metadata (OS/2's .TYPE EA): a roadmap proposal (`user.mime_type`).
- Self-tests `templates`, `ext`; `tests/comp/desktop-menu.sh` and `background.sh` click one row lower (New).

## Step 9. Font Palette and the Sound object (M) (VM)

1. **Font Palette** in System Setup: samples, Edit font..., drops onto folder windows, the desktop, the WarpCenter, menus and title bars (design 10).
2. **Sound object:** the event list with Sound file, Play, None.

**Checks:** a headless drop of a font on a folder (its titles drawn in it; kept after reopening), on title bars; the Sound page plays an event (a PipeWire null sink, as the G3 tests do).

**As built:**

- **Fonts by name** (`ui_font_named("12.Helvetica Bold")`): slots beside the interface font, kept when GNOME's font changes; rows, title lines and menu items grow with a larger font (the interface font's sizes as before).
- **The Font Palette** (WPFontPalette, a settings object in System Setup; existing users get it at the next start): its window of 12 samples drawn in their fonts; drag one (button 2) onto
  - a folder window or the desktop: that folder's **Icon font** (its Icon view page shows it); with **Shift**, every folder's (System: Fonts page);
  - a title bar: every title bar's (the compositor's frames too);
  - the WarpCenter: its font (the WarpCenter object's Font page).
  - Menus have no place to drop on: a sample's menu has **Use for menus** (and title bars, every folder, the WarpCenter; and the interface font everywhere again).
  - **Edit font...** (button, a sample's menu, or a double click): family list (fontconfig's; Sans, Serif, Monospace first), size, Bold, Italic, a preview; the samples are kept in the Font Palette object.
- **The Sound object:** each event is a sound field: a theme sound's name or a file, **Browse...** (the sound theme's folder first), **None**, **Play**. Play reads what the build can decode (Ogg needs libsndfile, which the RPM has).
- Self-tests `fonts`, `soundpage`.

## Risks

- **Sorting a huge folder by size or date** stats every entry: a worker in chunks, with the unsorted view meanwhile; the bound is checked in a unit test.
- **The search field** competes with type-ahead (typing in a folder selects by name today). **Mitigation:** type-ahead stays when the field is empty and not focused; Ctrl+F focuses the field.
- **Open With and `mimeapps.list`** are shared with GNOME: WPS writes only the user's file, and only for Always use.
- **Fonts dropped onto windows** need every WPS window to take per-window fonts; the widget set reads one interface font today.
