# Version 0.2 design: the OS/2 desktop, installable

Draft v0.1, 2026-11-21. The objectives are the owner's, in [roadmap.md](roadmap.md), "Objectives for 0.2". This document says how each is built on version 0.1. The implementation plan is [v0.2-plan.md](v0.2-plan.md).

The open choices in the roadmap are settled here as proposed there (the owner found the roadmap reasonable): each is marked **Decided** where it comes up, and can still be changed before its step is built.

## 1. Principles for 0.2

- **Objects, not special windows.** Everything new is an object with a class, a menu, a notebook and an icon, found by the same API (`resolve`, `list`, `menu`, `open`, `settings`), so the desktop, folders, Find and drag and drop work on them unchanged. New windows (the WarpCenter, the Messages list) are views of objects.
- **Built on what is there.** The trash, volumes, desktop entries, central objects, shadows, jobs and the settings objects already exist in wpsd; 0.2 adds classes and folders on top of them, not new stores.
- **Both modes where it makes sense.** Objects (Trash Can, Computer, Drives, Programs, System) work inside GNOME and in the WPS session. The WarpCenter and the notification service are WPS-session only in 0.2 (GNOME has its own bar and notifications).
- **Existing users keep their desktop.** A desktop made by 0.1 is brought along at the first 0.2 start, never rebuilt.
- **Installable at every step.** The groundwork (section 11) comes first, so each later step can be packaged and tried.

## 2. The default desktop

A new user's desktop holds, after the first start:

| Object | What it is |
|---|---|
| **System** | a folder (OS/2's "OS/2 System"): Computer, Drives, Minimized Window Viewer, LaunchPad, WarpCenter, System Setup, Startup |

In the WPS session the WarpCenter is shown at start and the LaunchPad is not (section 10).
| **Programs** | the installed programs, by category |
| **Trash Can** | the trash |
| **Templates** | a shadow of the Templates folder (as in 0.1) |

**Decided:** Computer lives in the System folder (as OS/2's Drives lived in OS/2 System); a shadow of it on the desktop is one drag away.

- **First start.** The desktop's first-start step (today `desktop_first_start` and `desktop_setup_shadow` in `wps-shell.c`, with marker files in `~/.config/wps`) moves into **wpsd**, as one versioned step: `<config>/desktop-made` gets a version line (`2`). wpsd makes the folders and objects (sections 4–7) and shadows of them on the desktop, then writes the marker. The desktop only opens.
- **0.1 desktops** (marker without a version, or version 1): the System Setup shadow on the desktop is replaced by a shadow of the System folder (System Setup moves inside it); Programs and Trash Can are added at free spots. Nothing the user made is touched; a step the user undid (a deleted shadow) is not redone once the marker says 2.

## 3. Live folders

Trash Can, Drives and Programs show contents that wpsd follows from outside WPS (the trash folders, udisks, the desktop entries). One mechanism for the three:

- **A live folder is a real folder in WPS's data** (`$XDG_DATA_HOME/wps/...`), so listing, icons, positions, views, Find and drag and drop work as for any folder.
- **wpsd keeps its contents in step** with their source: it makes, updates and removes the objects in it (shadows or central objects) as the source changes, and the usual change events reach the windows.
- **The user cannot drop arbitrary objects into it.** A live folder's class refuses drops that would not belong (Drives takes none; Programs takes shadows of programs, which the user may add; the Trash Can turns a drop into "move to the trash").

| Folder | Where | Contents | Source |
|---|---|---|---|
| Trash Can | (see 4) | the trash's items | the freedesktop trash: `~/.local/share/Trash` and each volume's `.Trash-UID` |
| Drives | `wps/Computer/Drives` | one WPDrive central object per volume | udisks2 (section 5) |
| Programs | `wps/Programs` | category folders with shadows of programs | desktop entries (section 6) |

## 4. Trash Can

- **Class `WPTrashCan`** (WPFolder). One object, the desktop's, in `wps/Trash Can` (a folder). Its view lists the trash's items, not the folder's own files: wpsd's `list` on a Trash Can returns the entries of every trash folder the user has (home's and mounted volumes' `.Trash-UID`), each row with:
  - the item's name in the trash;
  - its **original path** and deletion date, from `info/*.trashinfo`;
  - a title, the original name (so `notes.txt`, not `notes.txt.2`).
- **Its details view** has Origin and Deleted columns (the details-view columns of 0.3 come later; 0.2 adds these two for this folder only).
- **Menu:**
  - The Trash Can: **Empty trash** (asks first: "Delete N objects permanently?"), Open, Properties.
  - An item in it: **Restore** (back to its original folder; a name clash asks as a move does), **Delete permanently**.
- **Icon:** empty or full, following its contents (an `in_use`-like event when it goes empty or not).
- **Drops:** objects dropped on the Trash Can (icon or window) go to the trash, as Delete does (no move into the folder). Shadows dropped there are deleted, as OS/2 did.
- **Empty** is a delete job (jobs.c), with progress in the window and a journal; it empties every trash folder of the user's.
- **GNOME:** the same trash folders as GNOME's Trash, so both show the same items.
- **Shredder:** not carried over (the owner's decision).

## 5. Computer, Drives and disk objects

- **`WPComputer`** (WPFolder) in `wps/Computer`, holding **Drives** (a folder) and **/** (a WPDrive for the root file system). Its notebook shows the machine: host name, operating system, kernel, processors, memory (read only).
- **`WPDrives`** (WPFolder), a live folder of **`WPDrive`** central objects, one per volume:
  - a partition or whole disk with a file system;
  - internal and external, removable included;
  - not swap, not LVM physical volumes;
  - LUKS containers shown locked until unlocked.
- **A WPDrive's identity is its volume's UUID** (the file system UUID; for btrfs subvolumes, as wpsd's volumes already have it: UUID plus `:<root>`). **Decided:** central objects, not files; their positions and icons are kept like any object's.
- **Title:** the volume's label, else its size and kind ("500 GB Volume", "USB Drive"), as GNOME's Files names them.
- **Kinds and icons:**
  - hard disk, SSD, USB stick, optical, SD card, network-mounted (later);
  - the root file system;
  - mounted or not.
- **Opening** a drive opens its file system's top folder, mounting it first if it is not mounted (udisks2's Mount, which mounts removable volumes for the active session's user without a password; others ask through polkit).
- **Menu:**
  - **Open**; **Mount** or **Unmount**; **Eject** (removable), **Power off** (USB drives);
  - **Unlock** (LUKS: asks the passphrase);
  - **Properties:** device, file system, size, free space, mount point, UUID.
- **Following changes.** wpsd talks to **udisks2** over D-Bus (`org.freedesktop.UDisks2`, its ObjectManager): InterfacesAdded and Removed for drives plugged in and out, PropertiesChanged for mounts. A drive pulled out leaves its object ("not present") or removes it.
  - **Decided:** removed, as GNOME's Files does; a drive seen before comes back in the same place, by its UUID.
- **Without udisks2** (a minimal system), Drives shows the mounted file systems from mountinfo (wpsd's volumes) and cannot mount.
- **Root `/`** is a WPDrive for the root file system, opening `/`.

## 6. Programs

- **`WPProgramsFolder`** (WPFolder), a live folder in `wps/Programs`, made of **category folders** (Accessories, Development, Games, Graphics, Internet, Office, Multimedia, System, Settings, Other) holding shadows of the installed programs' desktop entries.
- **Sources:** `XDG_DATA_DIRS`/applications and `~/.local/share/applications` (Flatpak's exports included, as they are in `XDG_DATA_DIRS`).
  - Entries with `NoDisplay=true` or `Hidden=true` are left out, and so are those whose `OnlyShowIn`/`NotShowIn` exclude the desktop (XDG_CURRENT_DESKTOP=WPS inside the WPS session, GNOME inside GNOME).
- **Category:** the first of the entry's `Categories=` main categories that maps to a folder (the freedesktop menu's main categories, AudioVideo to Multimedia, Utility to Accessories, ...); none: Other.
- **Following changes:** wpsd watches the application folders (inotify): an installed program's shadow appears in its category, a removed one's goes.
- **The user's own** (**Decided**): the user may add shadows (of programs, or anything) and folders; wpsd leaves what it did not make alone, and never re-adds a shadow the user deleted (it remembers what it made, by desktop file ID).
- **Titles and icons** are the entries' `Name` and `Icon` (as programs already show).
- **The WarpCenter's start menu** shows the desktop (section 8); Programs is in it as a cascade.

## 7. The System folder and Startup

- **System** (`wps/System`, a WPFolder) holds:
  - **Computer** (section 5), with **Drives** inside; a shadow of Drives in System too, as OS/2 had Drives there.
  - **Minimized Window Viewer** (`WPMinWinViewer`, WPAbstract): opening it shows the minimized windows (today the desktop menu's "Minimized windows", from the Window List); its notebook has none of its own.
  - **LaunchPad** and **WarpCenter** (section 10): opening one shows it, its notebook holds its settings.
  - **System Setup:** today's folder, moved in (the folder keeps its ID, so its settings objects stay).
  - **Startup** (section 7.1).
- **Names:** "System" (OS/2: "OS/2 System"). The title can be changed as any.

### 7.1 Startup

**Decided:** one place for both XDG autostart and OS/2's Startup folder.

- **Startup is a view of `~/.config/autostart`**, the XDG autostart folder (a WPFolder whose path is that folder; title "Startup").
- **Dropping a program** (a desktop entry, or a shadow of one) there makes an autostart entry: a copy of the `.desktop` file, with `X-WPS-Startup=true` (as GNOME's Tweaks does).
- **Dropping a script or executable** makes an entry with `Exec=` the script.
- **Dropping anything else** (a folder, a document) makes a shadow there: the WPS desktop opens those at login, after the desktop is up, as OS/2's Startup folder did. They are not `.desktop` files, so systemd's autostart generator ignores them.
- **Running:** the WPS session already runs the autostart entries (systemd); the desktop opens the shadows. Inside GNOME, GNOME runs the entries, and the desktop (started by the extension) opens the shadows.
- **Entries made by other programs** (VBoxClient, ...) show as ordinary program objects; disabling one (`Hidden=true`) is a check box in its notebook ("Start at login").

### 7.2 Open windows restored at login

As OS/2 reopened what was open when it shut down.

- **What is kept:** WPS's own windows - folder windows (the folder, view, size, position, scroll position), Find windows (folder and name searched), settings notebooks (the object and page).
- **When:** as they open, move, change and close (so a crash loses little), into `$XDG_STATE_HOME/wps/open-windows`; at logout the list stands as the session left it.
- **At login** the desktop opens them again, after the desktop itself. In the WPS session the compositor puts each where it was: the desktop asks with a `place <app-id> <title> x y` line before opening it, and the compositor places the next window that matches (Wayland does not let a program place its own windows). Inside GNOME the windows reopen and GNOME places them.
- **Setting:** "Restore open windows at login" (System's notebook), on by default.
- **Not in 0.2:** other programs' windows. Wayland has no settled session protocol and most programs do not restore themselves; restarting them (in the folder they were started from) is for later, with OS/2's Work Area folders (roadmap 0.3).

## 8. WarpCenter

OS/2 Warp 4's bar, in the WPS session.

- **A WPS window** (`org.wps.WarpCenter`) of the desktop process, as the LaunchPad is: a thin bar along the bottom or top edge of the first screen (**top or bottom** is its setting; left and right later).
- **The compositor:**
  - keeps it above normal windows;
  - gives it the edge's full width;
  - subtracts its height from the **usable screen area** that maximizing, placement and the desktop use (a new kind, `KIND_PANEL`, like `KIND_PALETTE`). (Not to be confused with OS/2's Work Area folders, roadmap 0.3.)
  - Fullscreen windows still cover it.
- **Inside GNOME** (**Decided:** WPS session only for 0.2): GNOME has its own top bar, and a Wayland program cannot reserve space there; the desktop does not open the WarpCenter under GNOME.

**Its parts, from left to right:**

| Part | What it does | Source |
|---|---|---|
| **Desktop button** | OS/2's WarpCenter button: a menu of the desktop's objects, folders as cascades (read as they open), Programs among them; Lockup, Shut down, Window list at its end | the desktop folder (`list`), lazily |
| **Window list button** | the Window List, as Ctrl+Esc | (existing) |
| **Tray** | other programs' status icons; clicking activates, button 2 their menu | StatusNotifierItem (below) |
| **Meters** | CPU, memory, disk activity and network as small bars; clicking opens a details pop-up | `/proc/stat`, `/proc/meminfo`, `/proc/diskstats`, `/proc/net/dev`, every 2 s |
| **Keyboard** | the current input source ("EN", "한", ...); clicking goes to the next, as Super+Space; button 2 lists them | the compositor (below) |
| **Messages** | an envelope with the count of unread messages; clicking opens Messages (section 9) | the notification service |
| **Clock** | the time (and date on hover); clicking opens a month calendar | local time, each minute |

- **The keyboard part** needs the compositor to say which source is current: the compositor sends a line to the desktop (`I <index> <name>`) when the source changes (keymap.c), and the desktop sends `keyboard next|prev|<index>` back. The source's short name is the layout's two letters, or the IBus engine's (`hangul`: "한").
- **The tray** is a **StatusNotifierWatcher** and **host**: the desktop owns `org.kde.StatusNotifierWatcher` on the session bus, programs register their items, and the WarpCenter draws each item's icon (by name from the icon theme, or its pixmap) and tooltip. Activate, SecondaryActivate and the item's menu go over **dbusmenu** (`com.canonical.dbusmenu`), drawn as a WPS menu.
  - It is the largest part; it comes last within 0.2 and may move to 0.3 (the plan says when).
- **Settings** (the WarpCenter object's notebook, section 10):
  - edge (top, bottom);
  - which parts show;
  - the clock's format (12/24 h, seconds, date);
  - meters' choice;
  - shown at start (yes; the LaunchPad's default is no in the WPS session, section 10).

## 9. Messages and notifications

- **The WPS session's notification service:** the desktop process owns `org.freedesktop.Notifications` on the session bus (only in the WPS session; GNOME has its own).
  - **Notify:** a pop-up near the WarpCenter's Messages part, in WPS's style: icon, summary, body (plain text, simple markup), and actions as buttons.
  - The pop-up stays the notification's timeout (default 6 s, urgent ones until dismissed).
  - CloseNotification; ActionInvoked and NotificationClosed back to the program.
  - Capabilities: `body`, `actions`, `persistence`, `icon-static`.
  - "Do not disturb" (the Messages object's setting) keeps them out of sight, still counted.
- **WPS's own messages** go the same way: what folder windows put in their status line and the desktop could not show ("Moved to the trash: 2 objects", "Cannot delete: ...", job results), as notifications from "Workplace Shell" (low urgency: counted, no pop-up unless an error).
- **The Messages object** (`WPMessages`, in System, and the WarpCenter's envelope):
  - opening it shows the list of messages, newest first, with program, time, summary and body;
  - unread ones in bold;
  - a message's actions as buttons, while its program still runs;
  - Delete, Delete all, mark read.
  - Kept in `$XDG_STATE_HOME/wps/messages` (the last 500), so they survive a login.

## 10. LaunchPad and WarpCenter as settings objects

- **`WPLaunchPad`** and **`WPWarpCenter`**: subclasses of WPSetup (the settings objects' class), one of each per user, central objects in System (made with the other settings objects, `setup_objects_work`).
  - Their settings are tables, as the other settings objects' are; the desktop applies them as it applies System's and Mouse's (`apply_setup_object`).
- **LaunchPad's settings** (OS/2's LaunchPad notebook):
  - shown at start;
  - edge: floating at the bottom centre (as now), or along an edge;
  - small icons;
  - text under the buttons;
  - float on top;
  - the OS/2 buttons shown (Lockup, Find, Shut down, Window list).
- **Decided by the owner (2026-11-21):** in the WPS session the **WarpCenter is shown by default and the LaunchPad is not**.
  - The LaunchPad stays an object in System: opening it, or its notebook's "Shown at start", brings it back.
  - A 0.1 user, who never chose, gets the new default too.
  - Inside GNOME, where there is no WarpCenter in 0.2, the LaunchPad is shown by default (as in 0.1), so there is still a bar.
  - **Later** (0.3 or after): the LaunchPad is updated to share features with the WarpCenter (its parts, settings and code).
- **Opening** the LaunchPad or WarpCenter object brings it up (shown again if it was closed).

## 11. Installation, paths and versions

### 11.1 Paths

Programs find each other and their data through **build-time paths with a run-time override**, so the same code runs from the source tree (tests, development) and from `/usr`:

| What | Installed | From the tree |
|---|---|---|
| `wps-shell`, `wpsctl`, `wps-session` | `/usr/bin` | `build/` |
| `wpsd`, `wps-watchd`, `wps-plughost`, `wps-compositor` | `/usr/libexec/wps` | `build/` |
| Default data: schemes, sounds, icons, wallpaper | `/usr/share/wps` | the tree's folders |
| User service `wpsd.service` | `/usr/lib/systemd/user` | written by `tools/install-extension.sh` |
| `wps-watchd.service` | `/usr/lib/systemd/system` | (optional) |
| The session `wps.desktop` | `/usr/share/wayland-sessions` | `tools/install-session.sh` |
| `/etc/pam.d/wps-lock` | `/etc/pam.d` | `tools/install-session.sh` |
| GNOME Shell extension | `/usr/share/gnome-shell/extensions/wps@wps-linux` | `tools/install-extension.sh` |
| Plug-ins | `/usr/lib64/wps/plugins` | `build/plugins` |

- `WPS_LIBEXECDIR`, `WPS_DATADIR` and `WPS_PLUGINDIR` are compiled in (`make PREFIX=/usr`), and the environment overrides them (`WPS_LIBEXEC`, ...).
- `tools/wps-session` becomes the installed `wps-session` and finds the compositor and desktop through these; run from the tree, it uses `build/` as now.
- `make install DESTDIR=...` puts everything in place; `make uninstall` takes it away.

### 11.2 Versions and upgrades

- **Version:** `0.2.0` in one place (`VERSION`), compiled into every program (`--version`), the protocol's ping answer, and the RPM.
- **The protocol** between the GUI and wpsd gets a version in `ping`; a GUI newer than its wpsd says so and asks for a new login (both come from the same package, so it shows only during an upgrade before logging out).
- **The object database** (`objects.db`, SQLite) gets `PRAGMA user_version`: 0.1's is 0 (or missing), 0.2's is 2.
  - wpsd brings an older database up step by step at start (each step in a transaction, after a copy `objects.db.v<N>.bak`).
  - It refuses a newer one with a clear message, instead of guessing.
- **Attributes on files** (`user.wps.*`) carry no version today; a version key is added for their format, and 0.2 reads 0.1's (they do not change in 0.2).
- **The first-start marker** gets its version (section 2).

### 11.3 The RPM

- **`wps.spec`** in `packaging/`: BuildRequires (meson-free: make, gcc, wlroots0.20-devel, wayland-devel, cairo, harfbuzz, freetype, fontconfig, libxkbcommon, pixman, libdrm, systemd-devel, sqlite-devel, pam-devel, pipewire-devel, libsndfile-devel, xcb, glycin...), Requires (udisks2, ibus optional, xorg-x11-server-Xwayland, gnome-settings via gsettings-desktop-schemas).
  - **Subpackages:** `wps` (core, desktop, session), `wps-gnome-shell-extension`.
  - **Scriptlets:** `systemctl --global enable wpsd.service` (user units), nothing per user at install; a user's first start does the rest.
- **Built** with `rpmbuild -ba` from a tarball (`make dist`), and in **mock** for a clean Fedora 45 root.
- **Decided** (published where): a **COPR** repository, so `sudo dnf copr enable <owner>/wps && sudo dnf install wps`; the `.rpm` files are also attached to the release on GitHub. The COPR project needs the owner's Fedora account.
- **Tried** on a fresh Fedora 45 VM: install, log in to WPS, log in to GNOME, upgrade from the previous build, remove.

## 12. Tests

- **Every new class** gets service tests in the M5 style (Python scenarios against a private wpsd):
  - Trash Can: list, restore, empty, drop.
  - Drives: a fake udisks2 on a private bus, plugging and mounting.
  - Programs: entries added, removed, hidden, categories.
  - Startup: drops make entries.
  - Messages: Notify, actions, persistence.
  - Database upgrade: a 0.1 database brought to 0.2.
- **GUI and compositor:**
  - **Headless scripts** (`tests/comp/run.sh`): the WarpCenter's usable screen area (a maximized window stops at it), the keyboard part following Super+Space, a notification's pop-up and the Messages count, the Trash Can's Empty and Restore.
  - **Self-tests** for the start menu.
- **Install:** `make install DESTDIR=` into a scratch root, and the RPM in mock; a VM run by hand for the session.

## 13. What 0.2 does not do

- **RDP** (after 0.2), **window frames for GTK 4 / libadwaita** (deferred), the **Network** object.
- The WarpCenter on the **left or right** edge, and **inside GNOME**.
- Details-view sorting and columns in general (only the Trash Can's two columns), the folder search field, Open With: 0.3.
